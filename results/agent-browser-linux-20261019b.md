# Re-delivery: the best browser-automation setup an AI agent can use on Linux (separate from the owner's personal browser)

**Read date for every fact below: 2026-11-17 (America/New_York).** This re-delivers the research from task agent-browser-linux-20261018, re-checked and updated to 17 Nov 2026, plus the extra comparison this task asks for: Playwright with a dedicated profile, browser-use, Steel/Browserbase (self-hosted), Chrome DevTools MCP, and newer options — judged on Linux support, logins/2FA handling, headful viewing, and licence. All research was done on public web pages only — no login, no account, no purchase, no messages or comments to anyone. Every fact carries a full https:// source link in plain text. Where a figure could not be verified on a page actually read, it is marked NOT FOUND or "unsure" rather than guessed.

## Short answer (reused from agent-browser-linux-20261018, still current)

Use **one rootless Podman container holding a real, headful Chromium with a persistent profile, streamed over Selkies, driven over CDP by Playwright, and exposed to the coding agent through an MCP server** — concretely the LinuxServer Chromium image (`lscr.io/linuxserver/chromium:latest`) with a bind-mounted `/config` volume, Playwright 1.65.1 over CDP, and chrome-devtools-mcp 1.13.0, with the viewer reachable only over Tailscale or an authenticated reverse proxy. The full reasoning, option-by-option comparison, and component list are in the agent-browser-linux-20261018 result; this file condenses that answer and adds the focused comparison below.

The finding that drives everything: **since Chrome 136, `--remote-debugging-port` is ignored for the default Chrome data directory, so an agent gets its own separate profile and must sign in separately inside it** (https://developer.chrome.com/blog/remote-debugging-port — published 17 March 2025, read 2026-11-17). A dedicated agent profile is therefore the supported shape, not a workaround — and it is what keeps the crew's brand-account logins in their own profile, separate from any human's personal browser.

## 1. The focused comparison this task asks for

### 1a. Playwright with a dedicated profile

- **Version:** **1.65.1, released 13 November 2026** (1.65.0 was 5 November 2026) (https://en.wikipedia.org/wiki/Playwright_(software) — read 2026-11-17; https://playwright.dev/docs/next/release-notes — read 2026-11-17). Bundled browsers in 1.65: Chromium 158.0.8127.18, Firefox 159.0, WebKit 27.2; also tested against Google Chrome 157 and Microsoft Edge 156 (https://playwright.dev/docs/next/release-notes — read 2026-11-17).
- **Linux support:** "Playwright supports Chromium, WebKit and Firefox on Windows, Linux and macOS, locally or in CI, headless or headed, with native mobile emulation for Chrome (Android) and Mobile Safari" (https://playwright.dev/docs/intro — read 2026-11-17). Linux requirements in the current docs: Node.js latest 22.x, 24.x or 26.x; Debian 12/13, Ubuntu 22.04 / 24.04 / 26.04 (x86-64 or arm64). Node.js 20 is no longer tested as of 1.65 (https://playwright.dev/docs/intro — read 2026-11-17). Fedora is not in Playwright's listed distro set — the Docker image / `install --with-deps` route is the documented fallback; see "Unsure about".
- **Logins / 2FA:** `browserType.launchPersistentContext(userDataDir, …)` "creates a new BrowserContext with a specific user data directory… reuses the same profile every time you launch it, preserving cookies, cache, and other data" (https://runebook.dev/en/docs/playwright/api/class-browsertype/browser-type-launch-persistent-context — read 2026-11-17). A persistent directory is locked to one process at a time — same source. Alternative: `context.storageState()` save/load of cookies + localStorage — same source. Normal `browser.newContext()` is incognito-like (empty each run) (https://www.devtutorials.ai/learn/playwright/advanced/playwright-library-and-advanced-browser-control — read 2026-11-17). 2FA itself is a human step (or TOTP from a vault) — Playwright has no 2FA automation of its own; the profile just preserves the resulting session. `chromium.connectOverCDP()` attaches to a Chrome started with `--remote-debugging-port` (https://www.devtutorials.ai/learn/playwright/advanced/playwright-library-and-advanced-browser-control — read 2026-11-17).
- **Headful viewing:** headless by default; `--headed` / `headless: false` shows the window (https://playwright.dev/docs/running-tests — read 2026-11-17). UI Mode (`npx playwright test --ui`) gives "watch mode, live step view, time travel debugging"; `page.screencast` (since 1.59) records/overlays in real time; `browser.bind()` (since 1.59) shares a browser with the CLI and MCP (https://playwright.dev/docs/intro — read 2026-11-17; https://playwright.dev/docs/next/release-notes — read 2026-11-17). On Linux CI, "headed execution requires Xvfb… add `xvfb-run` before the actual command"; Playwright's Docker image and GitHub Action have Xvfb pre-installed (https://playwright.dev/dotnet/docs/ci — read 2026-11-17).
- **Anti-bot:** no built-in stealth mode. "Playwright does not have a native stealth mode" — community packages `playwright-stealth` (Python) / `playwright-extra` + `puppeteer-extra-plugin-stealth` (Node) patch leaks (https://www.scrapeless.com/en/blog/avoid-bot-detection-with-playwright-stealth — read 2026-11-17). One small measured study (21 Oct 2026, 80 page loads, local test page only) found Playwright's default headless shell differed from a normal Chrome on 13 of 15 checks, while "Playwright attached over the DevTools protocol to a Chrome we had started ourselves differed on none" (https://proxy.wiki/research/bot-detection-signals-measured/ — read 2026-11-17). That is a fingerprint-visibility measurement, not a guarantee any given site will or won't block it.
- **Licence:** Apache-2.0, Microsoft (https://docs.oracle.com/en/database/oracle/agent-factory/25.3/pafli/Microsoft_Corporation_playwright_test.html — read 2026-11-17).
- **MCP:** ships its own MCP server since 1.62 — `npx playwright mcp` (see §2).

### 1b. browser-use

- **Version: 1.0.6** (stable). The 1.0.0 stable release was published 10 Nov 2026; 1.0.6 is the top entry on the releases page (https://github.com/browser-use/browser-use/releases — read 2026-11-17).
- **What changed in 1.0:** the library was rewritten (~136,866 lines deleted, "80% of the library deleted"). The agent now writes Python in one persistent REPL executed straight on the Chrome DevTools Protocol (CDP) — no DOM serializer, no action schema. It also ships a built-in "judge" (from 1.0.5) that reviews the run's last screenshots and final page and flags blocks, CAPTCHAs, or prompt injection even on successful runs (https://github.com/browser-use/browser-use/releases — read 2026-11-17).
- **Linux support:** the library runs locally against your own Chromium (`Browser('chromium')`) or your own open Chrome; Docker images `browseruse/browseruse:1.0.0` and `ghcr.io/browser-use/browser-use:1.0.0`, smoke-tested on amd64 and arm64 (https://github.com/browser-use/browser-use/releases — read 2026-11-17). No Linux-specific limitation was found on the pages read.
- **Logins / 2FA:** cloud browsers support saved profiles (`profileId`) — "Cookies, localStorage and logins persist across browsers with profileId." Locally, `browser-use connect` attaches to the user's existing Chrome, preserving logins/cookies; `--profile` launches Chromium with a chosen Chrome profile's data (cookies, logins, extensions). Secrets can be passed via `sensitive_data=` with `type_secret()` and are redacted from outputs (https://browser-use.com/cloud-browser — read 2026-11-17; https://www.vybify.com/skills/browser-use-browser-use-browser-use/ — read 2026-11-17). **Caution for this use case:** default `Browser()` in 1.0 is now a **cloud** browser — local use needs an explicit choice, and the cloud default means brand logins would land on Browser Use's infrastructure unless you opt out (https://github.com/browser-use/browser-use/releases — read 2026-11-17).
- **Headful viewing:** CLI has `--headed` for a visible window; cloud browsers print a live-view link — every browser returns a `liveUrl` on live.browser-use.com: "Open it in a tab or embed it in an iframe; anyone with the URL can click and type in the live browser, so treat it as a credential." You can take over a login or CAPTCHA by hand there; MP4 recording available with `enableRecording` (https://browser-use.com/cloud-browser — read 2026-11-17; https://github.com/browser-use/browser-use/releases — read 2026-11-17). On servers/containers/CI with no display, `browser-use --cli-mcp` runs its own Chromium, installed on first use, instead of failing — an Xvfb recipe in Browser Use's own docs was NOT verified (https://github.com/browser-use/browser-use/releases — read 2026-11-17).
- **Anti-bot:** cloud browsers are real Chromium with stealth, CAPTCHA solving, residential proxies (195+ countries, $5/GB) built in. On Browser Use's own Stealth Bench V2 (100 bot-protected sites), Browser Use Cloud got through on 90.5% of visits vs Anchor 82% (https://browser-use.com/cloud-browser — read 2026-11-17; https://browser-use.com/alternatives/anchor — read 2026-11-17). Vendor benchmark — treat as vendor's own claim. Local/self-hosted runs do not get the cloud stealth/proxy/CAPTCHA layer.
- **Licence:** MIT for the open-source library and SDK; Browser Use Cloud is a proprietary service under its own terms (https://www.anchorterminal.com/compare/browser-use-vs-notte — read 2026-11-17).
- **MCP / API:** yes — `browser-use --cli-mcp` runs an MCP server (tools include `browser_exec`, `browser_screenshot`, `browser_login`); there is also a `browser-use` CLI that pipes Python to the browser harness, and `browser-use skill install` registers an agent skill (https://github.com/browser-use/browser-use/releases — read 2026-11-17).
- **Cloud pricing (general terms):** cloud browser $0.06/browser-hour with no subscription (per the cloud-browser page; an older comparison page says $0.02/hr — treat $0.06 as the current page figure). Default model in 1.0.6 is BU 4.0 at $1.80/$9.00 per 1M input/output tokens; `bu-fast` is $0.12/$0.60 (https://browser-use.com/cloud-browser — read 2026-11-17; https://github.com/browser-use/browser-use/releases — read 2026-11-17).
- **Security isolation:** 1.0.1 notes "each run gets its own browser-harness workspace." Domain restrictions (`allowed_domains`, `prohibited_domains`, `block_ip_addresses`) apply in every browser mode (https://github.com/browser-use/browser-use/releases — read 2026-11-17).
- **Resource use:** NOT FOUND as a stated figure (no published RAM/CPU per-browser numbers on the pages read).

### 1c. Steel / Browserbase (self-hosted)

**Steel Browser (steel-dev/steel-browser)**

- **Version: v0.5.5-beta, tagged 31 Oct 2026** (previous v0.5.4-beta, 25 Aug 2026). Still in public beta. **Flag: this version number rests on secondary release trackers (anchorterminal, everydev), not on a GitHub releases page read in this pass** (https://www.anchorterminal.com/compare/chrome-devtools-mcp-vs-steel — read 2026-11-17; https://www.everydev.ai/tools/steel-browser — read 2026-11-17).
- **What it is:** an open-source, self-hostable browser API server (Docker: `docker run -p 3000:3000 -p 9223:9223 ghcr.io/steel-dev/steel-browser`) that provisions headless Chromium sessions controllable via Playwright, Puppeteer, Selenium, or raw CDP. Steel Cloud is the managed version adding scale, stealth, proxies, and CAPTCHA solving (https://www.polylogin.com/en/blog/steel-dev-browser-api-sessions-profiles-pricing — read 2026-11-17; https://www.everydev.ai/tools/steel-browser — read 2026-11-17). The README says: "Steel is in public beta and evolving every day" (https://raw.githubusercontent.com/datascientistshiva/steel-browser/main/README.md — read 2026-11-17).
- **Linux support:** runs as a Docker container; no Linux-specific limitation found on the pages read. The self-hosted version "runs one session at a time and lacks the Credentials API and Files API that Steel Cloud provides" (https://www.polylogin.com/en/blog/steel-dev-browser-api-sessions-profiles-pricing — read 2026-11-17).
- **Logins / 2FA:** Profiles API — a profile stores cookies, extensions, credentials, localStorage, auth tokens, and fingerprints; starting a session with a `profileId` (and `persistProfile: true`) resumes logged-in state. Human-in-the-loop: open the `sessionViewerUrl`, do 2FA/CAPTCHA/SSO once, and the agent reuses that authenticated state. An independent test found a session "still logged in 27 days later" (https://steel.dev/blog/profiles — read 2026-11-17; https://gologin.com/blog/steel-tech-expert-review/ — read 2026-11-17). This is the best profile story of any option here for a crew keeping brand logins in their own profile.
- **Headful viewing:** NOT FOUND — Steel sessions are headless Chromium served remotely; you watch via the live viewer URL rather than a local window. Every session returns a `sessionViewerUrl` — a live player you open in your browser while the session runs to watch in real time; the CLI has a `live` command for the same (https://deepwiki.com/steel-dev/steel-cookbook/5.1-sessions-api — read 2026-11-17; https://dev.to/niksa/stop-managing-browser-sessions-yourself-use-steel-and-convex-47le — read 2026-11-17). No headed-mode claim found on the pages read.
- **Anti-bot:** free-plan test passed 3 of 5 anti-bot sites with default US datacenter IP; CAPTCHA solving needs a $10 paid balance and solved 1 of 4 challenges in one independent test (reCAPTCHA v2 in 25.4 s; Turnstile, PerimeterX, DataDome failed). A "Stealth Browser" custom Chromium fork exists (enterprise on request) (https://gologin.com/blog/steel-tech-expert-review/ — read 2026-11-17; https://steel.dev/blog/launch-week-v3-recap — read 2026-11-17).
- **Licence:** Apache-2.0 for steel-browser and the Node/Python SDKs; the MCP server and CLI are MIT. No AGPL/SSPL trap (https://www.anchorterminal.com/compare/chrome-devtools-mcp-vs-steel — read 2026-11-17).
- **MCP / API:** yes — official MCP server (1.12.0, Oct 2026) and CLI (`steel dev` runs a local runtime; `steel-browser` skill for agents; a Pi/OpenClaw extension `@steel-dev/pi`) (https://www.anchorterminal.com/compare/chrome-devtools-mcp-vs-steel — read 2026-11-17; https://steel.dev/blog/we-gave-pi-agent-a-real-browser — read 2026-11-17). Status: active — changelog entry #038 dated 2 Oct 2026; 32 commits merged between v0.5.4-beta and v0.5.5-beta (https://steel.dev/changelog — read 2026-11-17).
- **Cloud pricing (general terms, Steel Cloud):** Launch plan $0/month + usage, $30 one-time credits (valid 90 days), 10 concurrent sessions, 15-min sessions; browser time $0.10/hr; proxies $10/GB (Launch) / $6/GB (Scale); Scale $250/month (https://www.polylogin.com/en/blog/steel-dev-browser-api-sessions-profiles-pricing — read 2026-11-17; https://gologin.com/blog/steel-tech-expert-review/ — read 2026-11-17).
- **Resource use:** one independent test measured median session startup latency 3,687 ms. No published RAM/CPU per session found (https://gologin.com/blog/steel-tech-expert-review/ — read 2026-11-17).

**Browserbase (hosted) — and why there is no self-hosted equivalent**

- **What it is:** managed cloud Chromium — each browser runs in a dedicated VM destroyed and recreated after every session; driven over CDP by Playwright, Puppeteer, Selenium, or Stagehand. Cloud-only (private cloud for large enterprise); no self-hosted equivalent (https://ecorpit.com/cloud-browsers-ai-agents-browserbase-steel-kernel-2026/ — read 2026-11-17; https://balazscsorba.com/blog/browserbase-stagehand — read 2026-11-17).
- **The Stagehand side is open, the cloud is not:** Stagehand (browserbase/stagehand) is the MIT-licensed SDK — `act()` / `observe()` / `extract()` / `agent()` primitives; v3 dropped the Playwright dependency for a direct CDP engine; v4 moved target management, state, and CDP dispatch into a browser extension inside the browser; TypeScript, Python, and Go SDKs; version **4.4.0** (announced 2026-11-04) (https://www.browserbase.com/blog/stagehand-v4 — read 2026-11-17; https://www.browserbase.com/blog/stagehand-v3 — read 2026-11-17; https://www.browserbase.com/changelog/stagehand-4-4 — read 2026-11-17; https://pypi.org/project/stagehand/0.5.2/ — read 2026-11-17). But "Every component outside the SDK is proprietary… no self-hosted equivalent of the proxy pool, the stealth layer, the captcha solver or the session recorder"; on-premises deployment is not offered (https://balazscsorba.com/blog/browserbase-stagehand — read 2026-11-17).
- **Linux support (Stagehand):** yes — runs "anywhere Node.js or Python runs — macOS, Linux, Windows", including headless servers and CI (https://www.aibrew.io/blog/ego-lite-vs-stagehand — read 2026-11-17).
- **Logins / 2FA:** Stagehand "supports persistent browser contexts and storage-state files locally, and Browserbase contexts" (encrypted, per the comparison). 4.4 adds `browser.disconnect()` — let go of a browser without closing it, reconnect later — and crash-safe sessions (watchdog needs Chrome 137+) (https://www.aibrew.io/blog/ego-lite-vs-stagehand — read 2026-11-17; https://www.browserbase.com/changelog/stagehand-4-4 — read 2026-11-17).
- **Headful viewing:** Browserbase sessions have a live view a human can take over, plus session recording/replay (https://www.taskade.com/blog/history-of-browserbase — read 2026-11-17; https://pypi.org/project/stagehand/0.5.2/ — read 2026-11-17).
- **Anti-bot:** stealth, proxies, and CAPTCHA solving are Browserbase-cloud features, not in the local SDK. The free plan has no CAPTCHA solving and no stealth mode (https://www.usagepricing.com/blueprint/browserbase — read 2026-11-17; https://balazscsorba.com/blog/browserbase-stagehand — read 2026-11-17).
- **Pricing (general terms, checked 15 Nov 2026):** Free $0/mo — 1 browser hour, 3 concurrent browsers, 15-minute sessions, 3 agent runs, 1,000 Search + 1,000 Fetch calls, $5 in model tokens, 7-day retention, **no CAPTCHA solving, no proxies, no stealth**. Developer $20/mo — 100 hours then $0.12/hr, 25 concurrent. Startup $99/mo — 500 hours then $0.10/hr, 100 concurrent. Scale custom. Paid sessions last up to 6 hours (https://humanbrowser.cloud/blog/browserbase-alternative-2026 — read 2026-11-17; https://www.usagepricing.com/blueprint/browserbase — read 2026-11-17).
- **Licence:** proprietary hosted service; only the Stagehand SDK is open source (MIT) (https://balazscsorba.com/blog/browserbase-stagehand — read 2026-11-17).
- **MCP:** Browserbase offers a hosted MCP server; LangChain ships `langchain-stagehand` on PyPI (https://www.taskade.com/blog/history-of-browserbase — read 2026-11-17; https://www.browserbase.com/changelog/stagehand-4-4 — read 2026-11-17).

### 1d. Chrome DevTools MCP (Google)

- **Version: 1.13.0, released 2026-11-11** (adds logpoints and page-scoped network mocks) (https://www.stags.cn/releases/chrome-devtools-mcp/1.13.0/ — read 2026-11-17; https://aifrontierpost.com/articles/chrome-devtools-mcp-coding-agents-tutorial/ — read 2026-11-17). Repo: 58,074 stars, 65 releases, 1,626 commits, created 2025-09-11, not archived. Public preview announced 23 Sep 2025; stable 1.x line from 19 May 2026 (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17; https://www.irurueta.com/web/e2e-testing/ai-agents/chrome-devtools-for-agents.html — read 2026-11-17).
- **What it is:** "Chrome DevTools for agents (`chrome-devtools-mcp`) lets your coding agent (such as Antigravity, Claude, Cursor or Copilot) control and inspect a live Chrome browser. It is available as a Model-Context-Protocol (MCP) server and as a CLI" (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17).
- **Linux support:** requirements are Node.js LTS, current stable Chrome or newer, npm (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17). Officially supports Google Chrome and Chrome for Testing only; other Chromium browsers "may work, but this is not guaranteed" — same source. **Default is headed** (`--headless` default `false`) (https://www.irurueta.com/web/e2e-testing/ai-agents/chrome-devtools-for-agents.html — read 2026-11-17) — so on a headless Linux host it needs a display (Xvfb) or `--headless`.
- **Logins / 2FA:** yes, by default. Default profile is `$HOME/.cache/chrome-devtools-mcp/chrome-profile` (Linux/macOS), "not cleared between runs and shared across all instances… cookies and logins survive" (https://www.irurueta.com/web/e2e-testing/ai-agents/chrome-devtools-for-agents.html — read 2026-11-17; https://mcphub.com/mcp-servers/chromedevtools/chrome-devtools-mcp — read 2026-11-17). `--userDataDir` overrides it; `--isolated` uses a temporary dir deleted on exit (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17, via configuration guide summary at https://www.claudemarketplace.net/mcp/chrome-devtools-mcp — read 2026-11-17). Can also connect to a running Chrome via `--browserUrl` / `--autoConnect` (Chrome 144+) or `--wsEndpoint` (https://zenn.dev/suwash/articles/chrome-devtools-mcp_20260524?locale=en — read 2026-11-17). 2FA is done by the human in the headed window (or by TOTP from a vault); the MCP server itself has no 2FA automation.
- **Headful viewing:** the headed Chrome window it opens is visible on the desktop; `screencast_start`/`screencast_stop` tools stream it to the agent; a human can click in the same window. With `--autoConnect`/`--browserUrl` the agent joins the human's already-open Chrome.
- **Tools exposed:** counts vary by version and opt-in flags. A live stdio test of 1.12.0 listed **32 tools** (`click`, `close_page`, `drag`, `emulate`, `evaluate_script`, `fill`, `fill_form`, `get_console_message`, `get_css_styles`, `get_network_request`, `handle_dialog`, `hover`, `lighthouse_audit`, `list_console_messages`, `list_network_requests`, `list_pages`, `navigate_page`, `new_page`, `performance_analyze_insight`, `performance_start_trace`, `performance_stop_trace`, `press_key`, `resize_page`, `screencast_start`, `screencast_stop`, `select_page`, `take_heapsnapshot`, `take_screenshot`, `take_snapshot`, `type_text`, `upload_file`, `wait_for`) (https://testedmcp.com/tools/chrome-devtools-mcp-google/ — read 2026-11-17). The full reference including opt-in categories is described as ~60 tools (https://netraptor.dev/guides/chrome-devtools-mcp — read 2026-11-17). `--slim` reduces it to 3 tools for basic browsing — same source.
- **How the agent calls it:** MCP client config runs `npx -y chrome-devtools-mcp@latest` over stdio; no account or API key. The server "will start the browser automatically once the MCP client uses a tool that requires a running browser instance" (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17). Also ships a `chrome-devtools` CLI and skills — same source. Under the hood: "Uses puppeteer to automate actions in Chrome" over CDP — same source.
- **Anti-bot:** it drives a real branded Chrome, so the browser itself is genuine; no stealth features are documented. Same caveats as any CDP-driven browser.
- **Licence:** Apache-2.0 (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17).
- **Security isolation:** explicit warning in the README — "`chrome-devtools-mcp` exposes content of the browser instance to the MCP clients allowing them to inspect, debug, and modify any data in the browser or DevTools. Avoid sharing sensitive or personal information" (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17). Usage statistics are collected by Google and **enabled by default**; opt out with `--no-usage-statistics` — same source. Performance tools may send trace URLs to Google's CrUX API (disable with `--no-performance-crux`) — same source.
- **Resource use:** NOT FOUND as a quantified figure. One Chrome + one Node MCP server process.

### 1e. Newer options (since the first task)

- **agent-browser (vercel-labs/agent-browser)** — open-source Rust CLI from Vercel Labs that lets AI agents drive Chrome via accessibility-tree snapshots and element refs; **Apache-2.0**; latest tagged release **v0.43.0 (12 Nov 2026)**, last push 17 Nov 2026; macOS/Linux/Windows; installs via npm, downloads Chrome for Testing. No stable release yet; one review flags security controls off by default and 840 open issues/PRs as of 8 Oct 2026 (https://aireviewrating.com/tools/agent-browser — read 2026-11-17; https://www.anchorterminal.com/tools/agent-browser — read 2026-11-17). Promising as a shell-driven CLI for coding agents, but pre-stable and security-controls-off-by-default — not the pick for brand logins yet.
- **browser-session-mcp (xav-ie/browser-session-mcp)** — an MCP server giving each agent its own isolated, long-lived Chrome session (own cookies/storage/tabs per session); for passwords/passkeys/2FA the agent sends the human a link to a live view, the human logs in, hands control back, and the agent never sees credentials. Anti-bot notes: no `Runtime.enable` tell, consistent UA/client hints, real mouse/keyboard input. Licence/version NOT FOUND on the page read (https://glama.ai/mcp/servers/xav-ie/browser-session-mcp/tree — read 2026-11-17). The design matches this use case well (per-agent profile + human-takeover link), but it is a small community project with no verified licence/version — evaluate before trusting it with brand accounts.
- **Nanobrowser (nanobrowser/nanobrowser)** — open-source browser agent as a Chrome/Edge extension: runs its own Planner + Navigator agents inside the extension on your API key or a local model via Ollama. **Apache-2.0**, free, no account. Latest release **v0.2.0, 2 Oct 2026** (https://browsentic.com/nanobrowser-alternative/ — read 2026-11-17). It lives in the user's real browser/profile — which is exactly the isolation problem for a crew keeping brand logins separate.
- **BrowserPilot (RAGEFULRHINO16/browserpilot)** — local browser-control engine for MCP-speaking agents: 50 tools over your existing Chromium profile or an isolated Playwright profile; **MIT**; no hosted service, no required API key or subscription. Public websites start unapproved; clicks/typing/uploads need one-use approval on your PC. Early public release, "not an independently audited security product." Version NOT FOUND on the page read (https://glama.ai/mcp/servers/RAGEFULRHINO16/browserpilot/tree — read 2026-11-17).
- **Skyvern 1.0.58 (15 Nov 2026)** — still actively maintained, but **AGPL-3.0** (network copyleft), telemetry on by default, cloud anti-bot withheld from the repo, and a High-severity RCE (CVE-2026-123783, published 6 Nov 2026) in the script sandbox (https://mcp.cve.now/archive/2026-11-06 — read 2026-11-17; https://agentgid.com/agents/skyvern/ — read 2026-11-17; https://www.reviewramble.com/github-repos/skyvern — read 2026-11-17). Not recommended for a crew's brand-login browser.

## 2. MCP servers and clean APIs — the short list

- **chrome-devtools-mcp 1.13.0** (Apache-2.0, Google): `npx -y chrome-devtools-mcp@latest`, stdio, no account/key; 32 tools in the 1.12.0 test, `--slim` to 3; headed by default; persistent profile; `--browserUrl`/`--autoConnect` to join a running Chrome (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17).
- **Playwright MCP v0.0.84 (31 Oct 2026)** (Apache-2.0, Microsoft): `npx @playwright/mcp@latest`, stdio or HTTP `--port 8931`, Docker image `mcr.microsoft.com/playwright/mcp`; 23+ tools, accessibility snapshots, headed by default, per-workspace persistent profile, `--cdp-endpoint` to attach to existing Chromium; README: "not a security boundary" (https://github.com/microsoft/playwright-mcp — read 2026-11-17; https://playwright.dev/mcp/configuration/options — read 2026-11-17).

- **Steel MCP server 1.12.0** (MIT): local runtime via `steel dev`, `steel-browser` skill, Pi/OpenClaw extension (https://www.anchorterminal.com/compare/chrome-devtools-mcp-vs-steel — read 2026-11-17).

## 3. Recommendation — one setup for a crew that keeps brand-account logins in its own profile

**Pick: the same stack as agent-browser-linux-20261018 — LinuxServer Chromium on Selkies in a rootless Podman container, Playwright 1.65.1 over CDP, chrome-devtools-mcp 1.13.0 as the agent interface — with one addition for a crew: Steel self-hosted as the profile/session layer if the crew wants a clean REST API and per-profile sessions instead of raw CDP.**

Why this, for a crew:

1. **The logins live in exactly one place, owned by the crew.** The agent's whole profile (cookies, logins, extensions, history) is the container's `/config` volume (`~/.config/agent-browser/config:/config`), which survives container recreation (https://docs.linuxserver.io/images/docker-chromium/ — read 2026-11-17). Nothing is in any human's personal browser — Chrome 136 makes that separation mandatory anyway (https://developer.chrome.com/blog/remote-debugging-port — read 2026-11-17). Back up `/config` encrypted; never commit it anywhere; never mount it into another container. It holds live session cookies for the brand accounts — treat it as credentials.
2. **Headful and watchable from any device.** Selkies streams the actual desktop (WebRTC opt-in, H.264/H.265/VP8/VP9/AV1; 2.2.0 published 1 Nov 2026) to any browser at https://host:3001 (https://www.linuxserver.io/blog/webtop-5-0-and-selkies-2-0-everything-everywhere-all-in-one-release — read 2026-11-17; https://newreleases.io/project/github/selkies-project/selkies/release/2.2.0 — read 2026-11-17). A crew member opens the viewer and takes the keyboard/mouse for any captcha, phone check, or 2FA prompt. **Never expose the viewer raw:** the LinuxServer images have **no authentication by default** and the web interface includes a terminal with passwordless `sudo` — anyone who can reach the GUI can gain root inside the container (https://docs.linuxserver.io/images/docker-chromium/ — read 2026-11-17). Put it behind Tailscale or an authenticated reverse proxy.
3. **The agent drives it over CDP, the crew watches the same screen.** Playwright 1.65.1 `connectOverCDP()` to the container's Chromium, CDP port on loopback only (the debug port has no authentication — "anything that can reach it has full control") (https://www.browserless.io/blog/chrome-remote-debugging — read 2026-11-17). A real headful browser driven over CDP is the closest to a normal browser in fingerprint terms (0 of 15 checks differed in the proxy.wiki measurement) (https://proxy.wiki/research/bot-detection-signals-measured/ — read 2026-11-17).
4. **The coding agent calls it over MCP.** chrome-devtools-mcp 1.13.0, `npx -y chrome-devtools-mcp@latest` with `--browserUrl` at the container browser's CDP endpoint, plus `--no-usage-statistics` (usage stats are on by default) (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17). Playwright MCP is the valid alternative if Firefox/WebKit or accessibility-tree snapshots are wanted.
5. **2FA for brand accounts:** sign in once per site through the Selkies viewer with a crew member doing the 2FA, and let the session persist. Where the agent must do 2FA itself, use TOTP secrets from the crew's vault (not in the repo, not in the image). For SMS/phone checks there is no reliable agent-only path — a human takes over in the viewer. Expect some sites (notably Google/YouTube) to challenge a fresh container profile and to re-challenge on IP or fingerprint change; keep each site's recovery options current.
6. **Licence-clean:** every component in the recommended stack is Apache-2.0 or MIT (Chromium, Playwright, chrome-devtools-mcp, Selkies MPL-2.0). No AGPL (Skyvern), no SSPL (Notte), no proprietary cloud holding the brand logins.

**The Steel variant (if the crew wants an API, not raw CDP):** run Steel self-hosted (`ghcr.io/steel-dev/steel-browser`) instead of driving CDP directly. You get a REST API, a Profiles API with `profileId` persistence (the best profile story in this comparison — a session "still logged in 27 days later"), a `sessionViewerUrl` per session for human takeover, and an MCP server — all Apache-2.0/MIT (https://steel.dev/blog/profiles — read 2026-11-17; https://www.anchorterminal.com/compare/chrome-devtools-mcp-vs-steel — read 2026-11-17). Trade-offs: still in public beta (v0.5.5-beta, secondary-sourced — verify on https://github.com/steel-dev/steel-browser/releases), sessions are headless (no headed window, only the viewer URL), self-hosted runs one session at a time, and it lacks the cloud Credentials/Files APIs (https://www.polylogin.com/en/blog/steel-dev-browser-api-sessions-profiles-pricing — read 2026-11-17). Use Steel when the crew's workflow is API-shaped (sessions, profiles, viewer links); use the Selkies container when the crew's workflow is desktop-shaped (a visible browser anyone can take over).

**What not to use for this:** Browserbase/Browser Use Cloud/Steel Cloud/Hyperbrowser/Anchor — they move brand-account logins onto someone else's infrastructure and metered cloud browsers (and Browser Use 1.0 defaults to cloud unless you opt out); Skyvern (AGPL-3.0, telemetry on by default, cloud anti-bot withheld, CVE-2026-123783 RCE published 6 Nov 2026); Notte (SSPL-1.0); Nanobrowser/BrowserPilot (live in the human's real profile, or early/audited-nowhere); the archived Puppeteer MCP; a second profile in a human's desktop browser (works, but shares the desktop session and dies with it — the container keeps the same profile separation and adds a real boundary).

**Container/viewer alternatives, in brief:** neko v3.2.0 (15 Oct 2026, Apache-2.0, WebRTC by default, simplest multi-user handover) is the closest runner-up to Selkies — pick it if multi-user control handover matters more than the computer-use API and the prebuilt `/config` persistence (https://github.com/m1k1o/neko — read 2026-11-17; https://hysenlabs.com/projects/m1k1o-neko — read 2026-11-17). Kasm Workspaces 1.19.0 is a full platform (PostgreSQL, privileged Docker-in-Docker), ephemeral by default, and overkill for one agent browser (https://docs.kasm.com/docs/reference/release-notes/1.19.0 — read 2026-11-17). Plain noVNC + Xvfb + x11vnc is the most composable DIY stack and the easiest to run rootless in Podman, but the least smooth viewer with no native multi-user control (https://novnc.com/noVNC/ — read 2026-11-17).
