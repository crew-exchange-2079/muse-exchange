# Open-source tools for tape libraries and large-scale storage: landscape, gaps, and project ideas

Research date: 2026-10-07. GitHub figures below were read from the GitHub API on that date (open-issue counts include open pull requests). Anything not confirmed from a page actually opened is marked UNVERIFIED.

## Summary

The low-level Linux tape stack is old, single-maintainer, and mostly in maintenance mode: mtx has had no upstream release since 2008, and the OSS LTFS implementation is single-drive only. Backup suites (Bareos actively, Bacula slowly, Amanda dormant) still drive libraries through shell scripts wrapping mtx and explicitly exclude cleaning handling. The clearest unfilled gaps are (1) TapeAlert/drive-health and cleaning tracking with metrics and alerting, (2) a human-readable live library slot/element map, and (3) a standalone checksum-verified tape copy/verify tool — all three are things vendors sell and open source largely does not have.

## 1. Landscape

### Low-level tools

**mtx** (with tapeinfo, loaderinfo, scsieject) — GPL-2.0. Controls SCSI media changers (inventory, load/unload, transfers) and reports drive info including TapeAlert flags ([SourceForge project](https://sourceforge.net/projects/mtx/); [tapeinfo man page](https://manpages.debian.org/unstable/mtx/tapeinfo.1.en.html)). Latest upstream release is **1.3.12, from August 2008** ([release announcement](https://sourceforge.net/p/mtx/news/2008/08/mtx-media-changer-tools-ver-1312-stable-released/)); effectively unmaintained upstream, with fixes circulating as distro patches. Pain points: `READ ELEMENT STATUS` fails on libraries with more than ~25,000 slots (an EMC-contributed patch was posted to the mailing list but never released) and users report truncated barcode readback ([mtx-general list](https://sourceforge.net/p/mtx/mailman/mtx-general/)).

**mt-st** — [github.com/iustin/mt-st](https://github.com/iustin/mt-st). The `mt` tape-control program plus `stinit` for initialising drive modes at boot. Latest release **v1.8 (2025-02-08)**, whose notes say it arrived after almost two years; last push 2026-05-31; **55 stars, 14 forks, 6 open issues** (GitHub API, 2026-10-07). Maintenance-only, essentially one maintainer. Open issue #31 (since Nov 2023) asks for support of the kernel's immediate-EOF modes ([issue](https://github.com/iustin/mt-st/issues/31)); issue #27 reports `mt status` anomalies on an LTO-9 setup with no response ([issue](https://github.com/iustin/mt-st/issues/27)). License: UNVERIFIED (GitHub detects NOASSERTION).

**sg3_utils** — [github.com/doug-gilbert/sg3_utils](https://github.com/doug-gilbert/sg3_utils). Large suite sending SCSI commands via the sg interface; tape-relevant members include `sg_logs` (log pages including TapeAlert and device statistics), `sg_read_attr` (LTO cartridge-memory/MAM attributes), `sg_inq`, and `sg_get_elem_status`. Latest release **1.49 (release commit dated 2026-07-18)** after 1.48 in Aug 2023; last push 2026-09-22; **60 stars, 35 forks, 31 open issues** (GitHub API). Actively maintained by a single author, but development happens in a private SVN with GitHub as a mirror, and the multi-year release gaps draw complaints (["Release, please", issue #62](https://github.com/doug-gilbert/sg3_utils/issues/62)). License is mixed GPL-2/BSD-2 per its man pages.

**LTFS reference implementation** — [github.com/LinearTapeFileSystem/ltfs](https://github.com/LinearTapeFileSystem/ltfs), BSD-3-Clause. FUSE-based implementation of the LTFS format (ISO/IEC 20919) with `mkltfs`, `ltfsck`, and `ltfs_ordered_copy`. Latest release **v2.4.9.0-10523 (2026-09-24)**, explicitly the open-source equivalent of IBM Storage Archive SDE 2.4.9.0; **356 stars, 111 forks, 95 open issues/PRs** (GitHub API). Active but IBM-driven: releases mirror IBM's commercial product, and the OSS build supports **standalone drives only** — library support is reserved for IBM's paid Library/Enterprise Editions ([IBM Redbook on Spectrum Archive editions](https://www.redbooks.ibm.com/abstracts/sg248090.html)). Pain points: per-vendor drive support lags hardware (below, §2), and a Sep 2026 issue documents segfaults on drives whose INQUIRY vendor ID is not IBM/HP/HPE/Quantum ([issue #650](https://github.com/LinearTapeFileSystem/ltfs/issues/650)).

**stenc** — [github.com/scsitape/stenc](https://github.com/scsitape/stenc), GPL-2.0. Manages hardware encryption on LTO-4+ drives (modes, key descriptors, audit log). Latest release 2.0.1 (2025-07-23); **95 stars, 21 forks, 16 open issues** (GitHub API). Maintenance-only; AIX support has been suspended since 2022 for lack of a contributor with hardware.

**smp_utils** — SAS-management-protocol tools; only indirectly tape-relevant (diagnosing SAS expanders in front of libraries), no tape/changer functions. Maintenance-only, same author and SVN-first model as sg3_utils ([Debian package page](https://packages.debian.org/unstable/smp-utils)).

### Backup suites and HSM

**Bareos** — [github.com/bareos/bareos](https://github.com/bareos/bareos), AGPLv3. The active Bacula fork: same Storage Daemon / Autochanger / `mtx-changer` script model, plus a dedicated tape package, just-in-time device reservation, WORM support and native NDMP ([docs](https://docs.bareos.org/bareos-20/TasksAndConcepts/NdmpBackupsWithBareos.html)). Very active: **25.1.1 released 2026-09-03**, repo pushed 2026-10-07; **1,261 stars, 317 forks, 94 open issues/PRs** (GitHub API). Pain points are inherited from Bacula (below) plus multi-drive/tape races in filed issues (e.g. [#2142](https://github.com/bareos/bareos/issues/2142), [#1866](https://github.com/bareos/bareos/issues/1866)).

**Bacula (Community)** — AGPLv3. Autochanger support delegates changer control to an `mtx-changer` shell script wrapping mtx; `btape` is the manual test tool ([manual](https://www.bacula.org/9.0.x-manuals/en/main/Autochanger_Support.html)). Latest stable **15.0.3 (2025-03-27)** — a slow cadence ([download centre](https://www.bacula.org/source-download-center/)). Documented limits: autochanger support **excludes cleaning, stackers and silos**, tapes must be pre-labelled by hand with a catalogued slot, and the changer script "may need per-changer adaptation". Canonical source is the project's own GitLab, so GitHub-style star/issue counts are UNVERIFIED.

**Amanda** — [github.com/zmanda/amanda](https://github.com/zmanda/amanda). Network backup to tape/disk/cloud with a generic scriptable changer interface. Latest community release **3.5.4 (Aug 2023)**; last repo push 2024-01-31; **272 stars, 121 forks, 102 open issues/PRs** (GitHub API). Mainline is effectively dormant.

**CERN Tape Archive (CTA)** — GPL-3.0-or-later. The only true HSM-scale OSS here: custodial tape archive behind EOS or dCache disk buffers, with centralised drive scheduling ([GitHub copy](https://github.com/cern-cta/CTA); development on CERN GitLab). Very active (commits on 2026-10-07). CERN migrated ~83 PB of ATLAS data to it in 2020 and runs ~340 PB custodial on tape ([StorageNewsletter](https://www.storagenewsletter.com/2020/10/09/cern-storage-gets-ready-for-run-3/)); STFC RAL (UK Tier-1) publicly documented adopting CTA to replace CASTOR ([CHEP 2021 paper](https://www.epj-conferences.org/articles/epjconf/pdf/2021/05/epjconf_chep2021_02074.pdf)). Its acknowledged weak spot is scheduling: the object-store scheduler handles FIFO well but non-FIFO operations need workarounds, and there is no tool to predict when a given tape will mount.

**mhvtl** — [github.com/markh794/mhvtl](https://github.com/markh794/mhvtl), GPLv2. Virtual tape library (kernel module + daemons emulating drives and a robot) for testing backup software without hardware. Active (last push 2026-09-30); **186 stars, 97 forks, 44 open issues/PRs** (GitHub API). The out-of-tree kernel module is its structural burden — recurring build breakage on newer kernels and a PR exploring pluggable backends to drop it ([#171](https://github.com/markh794/mhvtl/pull/171)).

### Monitoring (the thinnest layer)

- **node_exporter `tapestats`** — the maintained baseline: kernel counters from /sys/class/scsi_tape only. No TapeAlert, no log pages, no cartridge memory, no library inventory, no cleaning state ([node_exporter](https://github.com/prometheus/node_exporter)).
- **mcmilk/prometheus-tapedrv-exporter** — the only dedicated direct-attached-tape Prometheus exporter found: a shell script feeding node_exporter's textfile collector. **One commit (Sep 2025), 0 stars**, drive-only, no changer/slot or cleaning metrics ([repo](https://github.com/mcmilk/prometheus-tapedrv-exporter)).
- Searches for an mtx/changer/library exporter returned **no dedicated repository at all** — the changer side has no exporter to even evaluate.
- **waa/bacula-tapealert** — a Bacula script wrapper that reacts to TapeAlert flags (including 20 "Clean Now" / 21 "Clean Periodic") via sg tools; last commit Aug 2024, 1 star; it reacts to flags but keeps no cleaning counters or history ([repo](https://github.com/waa/bacula-tapealert)).
- Cartridge-memory (LTO-CM/MAM) readers are all one-shot decoders that track nothing over time (e.g. [philpem/nfc-ltocm](https://github.com/philpem/nfc-ltocm), read-only by design and not supporting type 4+ cartridge memories).
- Zabbix/Nagios coverage is scattered single-vendor SNMP templates and checks (e.g. one Nagios `clean` check for 2014-era IBM libraries); no standalone Grafana tape-library dashboard was found outside a NetBackup-API exporter bundle.

## 2. Gaps people keep hitting

1. **Drive health and cleaning tracking.** TapeAlert standardises 64 flags including "Clean now" (20), "Clean periodic" (21) and "Expired clean" (22) ([IBM TapeAlert flag reference](https://www.ibm.com/docs/en/ts4300-tape-library?topic=flags-tapealert-supported-by-drive)), and the data is readable today via `sg_logs`/`sg_read_attr` — but surfacing it with history, cleaning-cartridge use counts and alerts is a feature of proprietary suites (e.g. Dell NetWorker's per-device TapeAlert and last-cleaned attributes, [Dell docs](https://www.dell.com/support/manuals/en-us/networker/nw_p_nwadmin_19.10/Tape-alert?guid=guid-ea5a803c-f642-4403-a612-c668f6c8e438&lang=en-us)). No maintained OSS daemon polls it, tracks cleaning media, and alerts. Bacula/Bareos exclude changer cleaning handling entirely by design.
2. **A human-friendly library slot/element map.** Operators still eyeball `mtx status` text dumps; vendors sell the at-a-glance slot-status table/map (e.g. [Dell's Data Protection Advisor "Tape Library Slot Status" report](https://www.dell.com/support/manuals/en-us/data-protection-advisor/dpa_p_report_reference/tape-library-slot-status?guid=guid-0ca4a8da-32a9-430d-83db-0fb51e88a970&lang=en-us)). No maintained OSS equivalent over live element status was found; the nearest new projects catalog tape *contents* (e.g. [tapewrangler](https://github.com/firworksyt/tapewrangler)), not live changer state.
3. **LTO-9/10 friction in OSS tools.** LTO-9 first-load media initialisation averages ~40 minutes and can take up to 2 hours, must not be interrupted, and has broken backup software timing (Spectra [initialisation guide](https://support.spectralogic.com/documentation/default-source/user-guides/90940168_a_lto9-initialization.pdf?sfvrsn=f9874b85_6); Veritas documents NetBackup offlining drives over it, [article](https://www.veritas.com/support/en_US/article.100054109)). In LTFS, per-vendor LTO-9 drive support lagged for years of issues — HPE Ultrium 9 "unsupported drive" ([#491](https://github.com/lineartapefilesystem/ltfs/issues/491)), Quantum ULTRIUM-HH9 not supported ([#382](https://github.com/lineartapefilesystem/ltfs/issues/382)), a 2.4 README claiming LTO-9 support the code lacked ([#427](https://github.com/lineartapefilesystem/ltfs/issues/427)) — with fixes arriving via community PRs. LTO-10 removes backward compatibility entirely (an LTO-10 drive handles LTO-10 media only) ([Blocks & Files](https://www.blocksandfiles.com/tape/2025/05/30/latest-generation-lto-10-tape-arrives-at-spectra-logic/1593183)); OSS LTFS support for LTO-10 is UNVERIFIED — its public drive table tops out at LTO-9.
4. **LTFS usability.** It presents as a filesystem but punishes filesystem habits: directory browsing forces tape reads, index rewrites interrupt copies, and recovery leans on `ltfsck` rollback; media-archive users report copy/verification error storms traced to LTFS losing the drive mid-job ([Creative COW thread](https://creativecow.net/forums/thread/large-number-of-copy-and-verification-errors-in-lt-2/)). Demand is for hardening and guardrails, not replacement — other users praise LTFS as far more usable than tar ([HN comment](https://news.ycombinator.com/item?id=21065666)).
5. **Safe tape copy/verify.** Vendors sell proactive cartridge validation (e.g. HPE StoreEver Data Verification, [datasheet PDF](https://www.hpe.com/psnow/downloadDoc/HPE%20StoreEver%20Data%20Verification%20Software-c04111347.pdf?id=c04111347.pdf&isFutureVersion=true&ver=6&form=false&preview=false&print=&hf=regular&r=&section=&prelaunchSection=&softrollSection=&deepLink=&utm_source=&utm_medium=&utm_campaign=&utm_content=&utm_term=&originalObjectName=)) and standalone cloning appliances. In OSS, `ltfs_ordered_copy` optimises copy order but does no checksum verification, and backup-suite copy jobs are catalogue-bound; no maintained standalone "duplicate this cartridge and prove both copies match" tool was found — people fall back to `dd`/`tar` and hope.
6. **Metrics for tape, generally.** Beyond kernel counters there is no maintained Prometheus path for host-attached drives or libraries (§1), so TapeAlert state, mount/error counters and element state reach dashboards only via proprietary backup software or DIY scripts.

## 3. Demand signals

- **Scale of the installed base:** LTO shipments were 160.3 EB in 2025, the second-highest year ever ([The Register](https://www.theregister.com/storage/2026/09/02/tape-still-isnt-dead-but-shipments-slipped-by-16-exabytes-in-2025/5293813)).
- **Big OSS deployments are public:** CERN's CTA runs ~340 PB custodial ([above](https://www.storagenewsletter.com/2020/10/09/cern-storage-gets-ready-for-run-3/)); RAL adopted CTA; the dCache collaboration documents tape/HSM at DESY, EuXFEL, NDGF, TRIUMF, KIT and US-CMS sites and is working to make CTA easier for other sites to adopt ([Computing and Software for Big Science paper](https://link.springer.com/article/10.1007/s41781-025-00152-5)). Friedrich Schiller University Jena presented a production Bareos deployment driving a partitioned tape library ([OSBConf 2016 deck](https://github.com/bareos/OpenSourceBackupConference/raw/refs/heads/main/2016/osbconf2016-ThomasOtto-The-Backup-Report-of-the-Friedrich-Schiller-University-Jena.pdf)).
- **Repo gravity:** Bareos is the healthy centre (1,261 stars, releases through Sep 2026); LTFS draws steady issue pressure (95 open issues/PRs, new filings through Sep 2026) despite IBM-paced development; mhvtl's 186 stars show real demand for tape *testing* infrastructure; and the monitoring niche's best dedicated effort has 1 commit and 0 stars — an empty field, not a contested one (all GitHub API/repo pages, 2026-10-07).
- **New-project energy at the edges:** tape-content catalogs (tapewrangler), an LTFS GUI whose release notes tout an index viewer and LTO-9 support ([LTOG v1.1.0](https://github.com/rlaphoenix/LTOG/releases/tag/v1.1.0)) — users keep rebuilding the friendly layer the core stack lacks.

## 4. Top 3 project ideas (one engineer, 2–6 weeks of evenings each)

### 1. Tape health + cleaning tracker with a Prometheus exporter ("tapewatch")

- **Why:** The data already exists in every drive (TapeAlert log page, MAM attributes, load counts); only proprietary suites surface it with history and alerts (§2.1). Cleaning is a documented blind spot of both Bacula-lineage suites, and the OSS monitoring field is empty (§1). It complements rather than competes with Bareos/Bacula — those users are the audience.
- **Target users:** Bacula/Bareos/Amanda shops with a library; homelab/DataHoarder LTO owners; small archives.
- **MVP:** a single small daemon/CLI (Go or Python) that polls drives via `sg_logs`/`sg_read_attr` on an interval; persists per-drive and per-cartridge state (loads, TapeAlert history, cleaning-cartridge remaining uses, last-cleaned) in SQLite; exposes Prometheus metrics plus two or three example alert rules ("clean now", "cleaning cartridge expired", "drive error rate rising"); a `--once` text report mode for cron users; works with any drive sg3_utils can talk to, no library required.

### 2. Live library slot/element map web UI ("shelfmap")

- **Why:** The everyday pain of `mtx status` text is documented, vendors charge for the visual version, and no maintained OSS live map exists (§2.2). It is also a natural companion to idea 1 and demos beautifully in a README screenshot — how small OSS tools get noticed.
- **Target users:** anyone running a changer through mtx/Bareos/Bacula; homelab owners with surplus libraries.
- **MVP:** read-only web page rendering the library as a grid (storage slots, drives, mail slots) coloured by state, with barcode labels, drive loaded/empty and cleaning-tape highlighting; data from `mtx status` parsing first, `sg_get_elem_status` second; barcode search box; JSON/CSV export of inventory; 30-second auto-refresh; zero write operations in v1 (safety is a feature — it can never move a tape).

### 3. Checksum-verified standalone tape copy/verify tool ("tapeclone")

- **Why:** Generation migration is a recurring, deadline-driven job and LTO-10's total break in compatibility makes it urgent now (§2.3); verification products exist only commercially (§2.5). A tool that duplicates a cartridge (to a second drive, or via a disk spool) and produces a checksum manifest proving the copies match fills a gap every archive faces and backup suites don't cover outside their own catalogues.
- **Target users:** media/post-production archives on LTFS, broadcasters, universities and labs migrating LTO generations, DataHoarder users duplicating personal archives.
- **MVP:** stream copy for raw (tar/dd-style) tapes with a per-block-group SHA-256 manifest; a verify-only mode that re-reads a tape and checks it against a stored manifest; clear handling of filemarks and variable block sizes; progress + throughput display tolerant of shoe-shining; resumable run log so an interrupted overnight job can be checked rather than restarted. LTFS-aware file-level mode is the stretch goal, not v1.

**Runner-up (not counted):** contributing per-vendor LTO-9/10 drive support to upstream LTFS is genuinely needed (§2.3), but it depends on owning the hardware and on IBM-paced review, so it is a weaker solo project than the three above.
