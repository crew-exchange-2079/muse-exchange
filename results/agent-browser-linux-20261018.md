# The best way to give an AI agent its own persistent web browser on Linux (late 2026)

**Read date for every fact below: 2026-11-17 (America/New_York).** All research was done on public web pages only — no login, no account, no purchase, no messages or comments to anyone. Every fact carries a full https:// source link in plain text. Where a figure could not be verified on a page actually read, it is marked NOT FOUND or "unsure" rather than guessed. Version numbers are given only where a source page stated them; where a version rests on a secondary release tracker rather than the project's own releases page, that is flagged.

## Short answer

Use **one rootless Podman container holding a real, headful Chromium with a persistent profile, streamed over Selkies, driven over CDP by Playwright, and exposed to the coding agent through an MCP server**. Concretely: the LinuxServer Chromium image (`lscr.io/linuxserver/chromium:latest`, Selkies viewer) on Fedora rootless Podman, a bind-mounted `/config` volume as the agent's profile, Playwright 1.65.1 driving it over CDP, and chrome-devtools-mcp 1.13.0 (or Playwright MCP) as the agent's interface — with the viewer reachable only over Tailscale or an authenticated reverse proxy, never raw on the internet. Details and why, in section 4.

The single most important finding of this research: **there is no good way to share the human's own browser profile any more, and that is by design.** Since Chrome 136, `--remote-debugging-port` is ignored for the default Chrome data directory, so an agent gets its own separate profile and must sign in separately inside it (https://developer.chrome.com/blog/remote-debugging-port — read 2026-11-17). A dedicated agent profile is therefore not a workaround — it is the supported shape, and it is also what keeps the human's logins and the agent's logins from contaminating each other.

## 1. Option (a): Chromium or Brave in a rootless Podman container + persistent profile + live viewer

### 1a. neko (m1k1o/neko)

- **What it is:** "A self hosted virtual browser that runs in docker and uses WebRTC" (https://github.com/m1k1o/neko — read 2026-11-17).
- **Version / status:** v3.2.0, released 15 Oct 2026; v3.1.6 on 30 Sep 2026, v3.1.5 on 5 Aug 2026. Actively maintained, not archived, ~22,691 stars (https://hysenlabs.com/projects/m1k1o-neko — read 2026-11-17). Licence: Apache-2.0 (https://hysenlabs.com/projects/m1k1o-neko — read 2026-11-17).
- **Viewer:** WebRTC video streaming (not framebuffer-over-WebSocket), built-in audio, multi-participant control — the README lists smooth video, built-in audio and multi-participant control as advantages over Apache Guacamole / noVNC (https://github.com/m1k1o/neko — read 2026-11-17).
- **Browsers:** images for Firefox, Tor Browser, Waterfox, Chromium, Google Chrome, Ungoogled Chromium, Microsoft Edge, Brave, Vivaldi, Opera; also XFCE/KDE desktops (https://github.com/m1k1o/neko — read 2026-11-17). Exact bundled browser version numbers inside the images: NOT FOUND on the pages read.
- **Watch / take over:** an admin can take browser control at any time, kick/ban users and manage the session; users view the shared browser and request control, transferred by right-clicking a user's avatar ("Give Controls"). A human therefore completes a captcha or phone check in the same streamed browser the agent is using. No source read claims neko bypasses captchas (https://docs.vultr.com/public/doc-assets/pdfs/article/how-to-deploy-neko-self-hosted-virtual-browser-platform.pdf — read 2026-11-17).
- **Logins / cookies persist:** only if a profile volume is mounted, e.g. `./profile:/home/neko/.mozilla/firefox/profile.default` — "Persist Firefox settings, bookmarks, extensions and history across container restarts by mounting the profile directory." Without persistent storage, "bookmarks, cookies, and browsing history disappear when the container restarts" (https://blog.51sec.org/2021/03/install-neko-self-hosted-virtual.html — read 2026-11-17; https://docs.vultr.com/public/doc-assets/pdfs/article/how-to-deploy-neko-self-hosted-virtual-browser-platform.pdf — read 2026-11-17).
- **Headful without a desktop session:** yes — it runs inside Docker with its own X server in-container; the README notes it "does not need to run in a container; you could install neko on your host, connect to your X server and control your whole VM" (https://github.com/m1k1o/neko — read 2026-11-17).
- **Resource use:** no authoritative CPU/RAM figure read on the primary repo/docs. A secondary directory lists 4 cores / 3 GB as a requirement — treat as unsure / secondary only (https://selfhost.directory/project/neko — read 2026-11-17).
- **Anti-bot friction:** a real headful browser in-container is closer to a normal browser than headless automation, but neko itself adds no stealth layer in the sources read; driving it via Playwright/Puppeteer still exposes automation signals. No "passes Cloudflare" claim was found.
- **Isolation:** Docker container isolation — "mitigates risk of OS fingerprinting and browser vulnerabilities by running in container", and "no state is left on the host browser after terminating the connection… only video is shared" (https://github.com/m1k1o/neko — read 2026-11-17).
- **Security caveat:** CVE-2026-116679 — neko 3.0.0–3.1.5, legacy WebRTC data-channel improper authorisation, fixed in 3.1.5. Use 3.1.5 or newer (current read: 3.2.0) (https://vuldb.com/vuln/427495 — read 2026-11-17).

### 1b. noVNC and KasmVNC as viewers

**noVNC**

- **What it is:** "noVNC is both a HTML VNC client JavaScript library and an application built on top of that library… runs well in any modern browser including mobile browsers." It requires WebSockets support on the server; websockify is its sister WebSocket-to-TCP proxy (https://novnc.com/noVNC/ — read 2026-11-17; https://raw.githubusercontent.com/kasmtech/noVNC/master/README.md — read 2026-11-17).
- **Version:** novnc 1.3.0 on PyPI, uploaded 25 Jan 2026. A GitHub latest-release tag was NOT FOUND on the pages read (https://pypi.org/project/novnc/ — read 2026-11-17).
- **How it works in a container:** a VNC server (e.g. TigerVNC) captures the desktop on e.g. `:1`/5901; noVNC serves the HTML5 client; websockify bridges WebSocket to VNC TCP. Only the reverse-proxy port needs to be public (http://umatechnology.org/how-to-access-gui-applications-remotely-with-docker-and-caddy/ — read 2026-11-17).
- **Watch / take over:** a human opens the noVNC page in any browser and gets keyboard/mouse control of the same X display the agent's browser runs on — captchas and phone checks can be done live. It is not natively multi-participant like neko; the neko README states multi-participant control is "not natively supported by Apache Guacamole or noVNC" (https://github.com/m1k1o/neko — read 2026-11-17).
- **Persistence:** noVNC itself stores nothing; persistence is entirely the browser profile volume / VNC-server container's home directory.
- **Latency:** framebuffer-over-WebSocket, generally higher latency and lower smoothness than WebRTC video streaming; Kasm's comparison calls KasmVNC "significantly more responsive than basic VNC over the same bandwidth" (https://www.bigiron.cc/guides/kasm-workspaces-vs-rdp-vs-apache-guacamole — read 2026-11-17).
- **Isolation:** same container boundary as the browser it views; noVNC/websockify add a web-exposed surface that must sit behind HTTPS/auth — by default many example stacks have no auth.

**KasmVNC and Kasm Workspaces**

- **What KasmVNC is:** "KasmVNC provides remote web-based access to a Desktop or application… KasmVNC is accessed by users from any modern browser and does not support legacy VNC viewer applications." YAML configuration, GPL-2.0, 5,394 stars, not archived (https://github.com/kasmtech/KasmVNC — read 2026-11-17).
- **Version:** 1.5.2, as reported in the Kasm Workspaces 1.19.0 rolling notes: "(10/21/2026) Updated KasmVNC to 1.5.2, including bug fixes and security hardening." A standalone KasmVNC releases-page version was NOT FOUND directly in this pass — verify on the releases page before pinning (https://docs.kasm.com/docs/reference/release-notes/1.19.0 — read 2026-11-17). New in the 1.19 era: H.264, H.265 and AV1 video streaming modes for container-based Workspaces (https://docs.kasm.com/docs/reference/release-notes/1.19.0 — read 2026-11-17).
- **Watch / take over:** same model as noVNC (browser tab, streamed desktop, keyboard/mouse), with video-encoding modes, clipboard, and a built-in web server — "KasmVNC has a built in web server and the web code is baked into KasmVNC." Its bundled client is a fork of noVNC, modified for KasmVNC, and "will not work with legacy VNC servers" (https://raw.githubusercontent.com/kasmtech/noVNC/master/README.md — read 2026-11-17).
- **Kasm Workspaces version / status:** 1.19.0, actively maintained in 2026. Highlights: H.264/H.265/AV1 in KasmVNC, Guacamole 1.6.0, Intel/AMD GPU passthrough, NVIDIA MIG slices, full-stack Linux VMs over RDP, Kubernetes GA, new images (Fedora 42/43, Alpine 3.22/3.23, ParrotOS 7, OpenSUSE 16), Claude Code / Gemini CLI / Codex CLI / Cursor images (https://docs.kasm.com/docs/reference/release-notes/1.19.0 — read 2026-11-17). A secondary install guide states 1.19.0 is published "with maintenance until September 2027" — secondary, unsure for the exact EOL date (https://franklinetech.com/installing-and-using-kasm-workspaces/ — read 2026-11-17).
- **Model:** container streaming platform — pick a workspace (Docker image: Firefox, Chrome, Ubuntu Desktop, Kali, etc.), Kasm spins up a fresh container, interact via browser (KasmVNC/noVNC); "When you close the session, the container is destroyed." Community Edition free, "limited to 5 concurrent sessions" (https://www.bigiron.cc/guides/kasm-workspaces-vs-rdp-vs-apache-guacamole — read 2026-11-17).
- **Persistence:** ephemeral by default — "no persistence, so no saved logins" on the hosted cloud browser; self-hosted persistent profiles are opt-in via volume-mounted, S3-based, or Storage-Mapping (Kasm Profile Sync) profiles, with the user's home directory mapped in each session. Storage-Mapping profiles are in Preview and "not currently recommended for production use" (https://docs.kasm.com/docs/how-to/data-storage/persistent-profiles — read 2026-11-17; https://blog.send.win/low-cost-virtual-browser-8-picks-starting-at-2-a-month/ — read 2026-11-17).
- **Standalone images:** `kasmweb/desktop:1.18.0` (Ubuntu Jammy + Chrome/Firefox) and `kasmweb/brave:1.18.0` can run standalone: `docker run --rm -it --shm-size=512m -p 6901:6901 -e VNC_PW=password kasmweb/brave:1.18.0`, then https://host:6901. Note: `--rm` in that example means no persistence; audio/uploads/downloads/mic are only fully available under Kasm orchestration (https://hub.docker.com/r/kasmweb/desktop — read 2026-11-17; https://hub.docker.com/r/kasmweb/brave — read 2026-11-17).
- **Resource use:** default workspaces "configured to request 2768MB of memory and 2 cores" (secondary guide); a separate guide puts browser sessions at roughly 500 MB–1.5 GB RAM. Treat both as indicative, not measured (https://franklinetech.com/installing-and-using-kasm-workspaces/ — read 2026-11-17; https://www.selfhostedguides.com/kasm-browser-isolation/ — read 2026-11-17).
- **Verdict for this use case:** Kasm Workspaces is the right choice only if multi-user, policies, and persistent-profile management across users matter — it is a full platform (PostgreSQL, manager/proxy/agent, Docker-in-Docker, privileged mode in the LinuxServer kasm image), ephemeral by default, and overkill for one agent browser. LinuxServer's kasm image "requires being run in `privileged` mode" and uses Docker-in-Docker (https://docs.linuxserver.io/images/docker-kasm/ — read 2026-11-17).

### 1c. Selkies (selkies-project)

- **What it is:** "Low-Latency Accelerated Web Remote Desktop Streaming Platform for Self-Hosting, Containers, Kubernetes, or Cloud/HPC… streams over plain WebSockets by default, with WebRTC available as an opt-in transport." MPL-2.0, 2,579 stars, not archived. Explicitly "designed for researchers studying Agentic AI" among others (https://github.com/selkies-project/selkies — read 2026-11-17).
- **Version / status:** very active in 2026, despite a "we are in need of maintainers" banner on the repo/PyPI. Selkies 2.0.0 shipped 24 Sep 2026; 2.1.0 on 21 Oct 2026; **2.2.0 published 1 Nov 2026** (119 commits between 2.1.0 and 2.2.0). The LinuxServer blog notes "the Selkies repo alone took 804 commits and grew by 190,000 lines" in the five months before the 2.0 post, and the `lsio` branch was merged into `main` in June 2026 (https://newreleases.io/project/github/selkies-project/selkies/release/2.2.0 — read 2026-11-17; https://www.linuxserver.io/blog/webtop-5-0-and-selkies-2-0-everything-everywhere-all-in-one-release — read 2026-11-17; https://pypi.org/project/selkies/2.1.0/ — read 2026-11-17).
- **Streaming:** in 2.0, "WebRTC as a real first class transport next to our WebSockets protocol"; the WebRTC stack is a vendored fork of aiortc; codecs H.264, H.265/HEVC, VP8, VP9, AV1 over both WebSockets and WebRTC, on NVENC, VA-API, and in software. WebRTC is opt-in via env (`SELKIES_MODE=webrtc` or any TURN/STUN variable); WebSockets remains the default. Known limitation: "WebRTC behind NAT may still need a STUN/TURN server… The default WebSocket transport does not." Upstream desktop image embeds coTURN (https://www.linuxserver.io/blog/webtop-5-0-and-selkies-2-0-everything-everywhere-all-in-one-release — read 2026-11-17; https://newreleases.io/project/github/selkies-project/selkies/release/2.2.0 — read 2026-11-17).
- **Watch / take over:** HTML5 client in Chromium/Firefox/Safari, two-way clipboard, keyboard/mouse/gamepad, mic/webcam forwarding; session sharing is a listed web-client capability in LinuxServer images. A human opens the same session URL and takes the display — 2.2.0 adds display handover between pages/tabs ("a page of another tab or device takes its display once the owner's tab is hidden") (https://github.com/selkies-project/selkies — read 2026-11-17; https://newreleases.io/project/github/selkies-project/selkies/release/2.2.0 — read 2026-11-17).
- **Headful without a desktop session:** Selkies base supplies "the display servers (XLibre's Xvfb with glamor and DRI3, and the headless Wayland backend)", PipeWire audio, GPU runtime wiring, s6 supervision, and an embedded coTURN server. LinuxServer's 2.0 rebase replaced Xorg's Xvfb with XLibre's Xvfb and made Wayland (labwc) the default with X11 fallback (https://raw.githubusercontent.com/selkies-project/docker-nvidia-egl-desktop/main/README.md — read 2026-11-17; https://www.linuxserver.io/blog/webtop-5-0-and-selkies-2-0-everything-everywhere-all-in-one-release — read 2026-11-17).
- **Persistence:** Selkies itself is the streamer; persistence is the container's `/config` (LinuxServer) or home-directory volume. Upstream reference: `ghcr.io/selkies-project/selkies/desktop:latest-ubuntu26.04`, rootless at uid 1000, with embedded coTURN; Ubuntu 26.04 or Debian Trixie, amd64/arm64 (https://www.linuxserver.io/blog/webtop-5-0-and-selkies-2-0-everything-everywhere-all-in-one-release — read 2026-11-17; https://github.com/selkies-project/selkies — read 2026-11-17).
- **Agent-relevant extra:** LinuxServer's Selkies 2.0 post mentions "An AI agent that can drive the desktop" and a "Pelorus" computer-use API / accessibility stack exposed by the images (https://www.linuxserver.io/blog/webtop-5-0-and-selkies-2-0-everything-everywhere-all-in-one-release — read 2026-11-17; https://docs.linuxserver.io/images/docker-chromium/ — read 2026-11-17).

### 1d. Chromium / Brave in a rootless Podman container — the mechanics

- **Rootless Podman isolation model:** rootless containers run as a regular user without a privileged daemon; "Podman relies on user namespaces to map user IDs in the container to different user IDs on the host… the root user inside the container [UID 0] maps to the UID of the current user on the host." A container escape therefore gives at most that user's privileges, not host root. Requires `/etc/subuid`/`/etc/subgid` ranges and `newuidmap`/`newgidmap`; cgroups v2; rootless cannot bind ports <1024 by default; Podman 5.x uses `pasta` as the default rootless network backend (https://documentation.suse.com/smart/container/html/rootless-podman/index.html — read 2026-11-17; https://docs.rockylinux.org/10/guides/containers/rootless_podman_advanced/ — read 2026-11-17).
- **Headful-without-desktop patterns:**
  - **Xvfb (X11 virtual framebuffer):** "a virtual X server that runs without a physical display… allows GUI applications that use X Windows to run on a headless system." Standard recipe: `Xvfb :10 -screen 0 1920x1080x24`, `DISPLAY=:10.0`, then launch the browser headful; or `xvfb-run` (https://pypi.org/project/xvfbwrapper/ — read 2026-11-17; https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox — read 2026-11-17).
  - **Headless Wayland compositor (Weston/labwc):** WebdriverIO's runner starts "Weston in headless mode, or Xvfb as a fallback"; Weston starts without Xwayland, so it provides no `DISPLAY`; if tools need X11, use Xvfb. Chrome/Edge 140+ follow `XDG_SESSION_TYPE=wayland`; older builds need `--ozone-platform=wayland` (https://webdriver.io/docs/headless-and-display-servers — read 2026-11-17).
  - **Xwayland:** X11 apps under a Wayland compositor; Chromium can be forced with `--ozone-platform=x11` to run through XWayland instead of native Wayland (https://dev.clauneck.workers.dev/sizzlebop/i-fixed-webgpu-on-linux-then-forgot-how-i-did-it-5hjd — read 2026-11-17).
  - **Practical stack for watch/takeover:** "Xvfb owns the virtual display. Openbox manages the browser window. x11vnc exports the display. noVNC lets a human watch or take over in a browser." Headed and headless variants share the same CDP control channel (https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox — read 2026-11-17). Selkies/LinuxServer images prebuild this whole stack — XLibre Xvfb or headless Wayland (labwc) inside the image, no host desktop needed.
- **Persistent profile:** mount the browser's profile/home directory as a volume (Chromium `--user-data-dir`, Firefox profile dir, or the container's `/config` home). LinuxServer's Chromium wrapper "cleans up stale singleton locks so a recreated container does not hit the 'profile in use' dialog" and "Recreate the container against the same `/config`: settings persist, no first run dialogs" (https://docs.linuxserver.io/selkies/developer-guide/building-images/ — read 2026-11-17).
- **Chromium sandbox caveat in containers:** LinuxServer's wrapper uses `--no-sandbox` because "the container itself is the sandbox boundary and Chromium's own sandbox needs privileges the container deliberately lacks"; also `--password-store=basic` to avoid keyring prompts. That trades Chromium's internal sandbox for the container/user-namespace boundary — important for the isolation assessment (https://docs.linuxserver.io/selkies/developer-guide/building-images/ — read 2026-11-17).
- **Resource use:** each headless Chrome instance "eats 100–500 MB of RAM" (guide figure, indicative); a full streamed desktop adds the display server + encoder on top. No measured Podman+Chromium figure was read — NOT FOUND as a benchmark (https://webscraping.ai/blog/headless-browser-guide — read 2026-11-17).
- **Whether sites see a normal browser / anti-bot friction:** headful is materially less detectable than headless, but not invisible. Headless tells: `navigator.webdriver=true`, empty `navigator.plugins`, SwiftShader WebGL renderer instead of real GPU, 800×600 defaults, missing `window.chrome` runtime objects (https://alterlab.io/blog/playwright-bot-detection-what-actually-works-in-2026 — read 2026-11-17). "Headful is far less detectable than headless" and "run your real, installed Chrome with a persistent user-data profile instead of the bundled Chromium build — that gives the agent a genuine, consistent fingerprint." Playwright's Chromium also has a distinct TLS/JA3 fingerprint (https://aiworkshack.com/tools/browser-use/browser-use-and-anti-bot-detection-why-your-agent-gets-blocked-and-how-to-fix-it.html — read 2026-11-17; https://alterlab.io/blog/playwright-bot-detection-what-actually-works-in-2026 — read 2026-11-17). For aggressive protection (Cloudflare Enterprise, Akamai, PerimeterX), "no amount of local stealth configuration will reliably work" — TLS fingerprinting, IP reputation, behavioural analytics. Human takeover for the challenge itself remains the reliable path (https://aiworkshack.com/tools/browser-use/browser-use-and-anti-bot-detection-why-your-agent-gets-blocked-and-how-to-fix-it.html — read 2026-11-17).
- **Brave specifically:** Brave is Chromium-based and follows the same shape as Chrome/Chromium (install vendor package, same flags/systemd/CDP). A LinuxServer Brave image exists (`ghcr.io/linuxserver/brave:latest`, `/config` volume); one Synology guide notes it "works with the latest Brave v1.93.138 release" (Sep 2026 guide — that version is from the guide, not a live image check). Kasm also ships `kasmweb/brave`. No official Brave-maintained container image was found — NOT FOUND (https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox — read 2026-11-17; https://mariushosting.com/how-to-install-brave-on-your-synology-nas/ — read 2026-11-17; https://hub.docker.com/r/kasmweb/brave — read 2026-11-17).

Do not expose it to the Internet unless you have secured it properly… By default there is **no authentication**… the web interface includes a terminal with passwordless `sudo`, anyone who can reach the GUI can gain root inside the container." Put it behind a reverse proxy with robust auth (e.g. SWAG) / VPN / Tailscale, never raw on the internet (https://docs.linuxserver.io/images/docker-chromium/ — read 2026-11-17; https://docs.linuxserver.io/images/docker-firefox/ — read 2026-11-17).

**Podman note:** LinuxServer's own blog says its images are built for "Docker or Podman (Podman is best effort)". Rootless Podman + these images is therefore plausible but not a first-class supported path in the sources read; the `--no-sandbox` / privileged-access trade-offs above still apply (https://www.linuxserver.io/blog/webtop-5-0-and-selkies-2-0-everything-everywhere-all-in-one-release — read 2026-11-17).

**Bottom line for option (a):** LinuxServer Chromium/Firefox/Brave on Selkies, or neko, are the best fit for "agent drives it, human watches/takes over for logins and captchas": both single-container, actively maintained in Nov 2026, headful by construction, persistent via a mounted `/config` or profile directory. Selkies gives the more modern streamer (WebRTC opt-in, 5 codecs, GPU zero-copy, computer-use API); neko gives the simplest multi-user control handover and the lowest-latency WebRTC-by-default experience. Plain noVNC + Xvfb + x11vnc is the most composable / lowest-dependency DIY stack and the easiest to run rootless in Podman, but the least smooth viewer and with no native multi-user control.

(Fedora is not in Playwright's listed distro set — the Playwright Docker image / `npx playwright install --with-deps` is the documented route on other distros; see "Unsure about".)

A persistent directory is locked to one process at a time (error if already in use) — same source. Alternative: `context.storageState()` save/load of cookies + localStorage — same source. Note: normal `browser.newContext()` is incognito-like (empty each run) (https://www.devtutorials.ai/learn/playwright/advanced/playwright-library-and-advanced-browser-control — read 2026-11-17).

- **Headful without a desktop session:** on Linux CI, "headed execution requires Xvfb… add `xvfb-run` before the actual command"; Playwright's Docker image and GitHub Action have Xvfb pre-installed (https://playwright.dev/dotnet/docs/ci — read 2026-11-17). For a human to watch/take over a headless Linux box remotely, the established pattern is Xvfb + a window manager + noVNC (https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox — read 2026-11-17).

That is a fingerprint-visibility measurement, not a guarantee any given site will or won't block it.
- **Security isolation:** browser contexts are isolated (own cookies/cache/localStorage); persistent profile is single-writer. Playwright's own protocol (`launchServer`/`connect`) requires matching Playwright minor versions client/server (https://www.irurueta.com/web/e2e-testing/playwright/advanced-topics.html — read 2026-11-17).

## 4. Option (d): a second profile in an existing desktop browser driven over CDP

- **What it is:** the Chrome DevTools Protocol — the JSON-over-WebSocket protocol Chrome exposes for debugging/automation; the same protocol DevTools itself uses. A browser only listens if started with a debugging port (https://www.mosaicbrowser.com/guides/connect-to-an-existing-chrome-with-cdp — read 2026-11-17).
- **The Chrome 136 change (the key fact for this use case):** "from Chrome 136 we're making changes to the behavior of `--remote-debugging-port` and `--remote-debugging-pipe`. These switches will no longer be respected if attempting to debug the default Chrome data directory. These switches must now be accompanied by the `--user-data-dir` switch to point to a non-standard directory. A non-standard data directory uses a different encryption key" (https://developer.chrome.com/blog/remote-debugging-port — published 17 March 2025, read 2026-11-17). **Consequence: you cannot attach to your everyday default profile any more; you get a separate profile and must sign in to whatever the script needs inside it** (https://www.mosaicbrowser.com/guides/connect-to-an-existing-chrome-with-cdp — read 2026-11-17).
- **How it works in practice:** launch e.g. `google-chrome --remote-debugging-port=9222 --user-data-dir=/path/to/custom/profile` (quit ordinary Chrome first, or the launch is handed to the running instance and no port appears); then any CDP client (Playwright `connectOverCDP`, Puppeteer `connect`, raw WebSocket, or DevTools itself) attaches. Multiple clients can attach at once — "your script and the DevTools window can watch the same tab" (https://www.mosaicbrowser.com/guides/connect-to-an-existing-chrome-with-cdp — read 2026-11-17).
- **Logins / cookies persist:** yes, inside that separate `--user-data-dir`, like any Chrome profile — "Close Chrome and reopen it with the same `--user-data-dir`, and all your sessions are still there" (https://www.innateblogger.com/2026/03/connect-ai-agent-chrome-devtools-mcp.html — read 2026-11-17). They do **not** carry over from your main profile; that isolation is the point.
- **Watch / take over:** directly — it is a normal visible Chrome window; the human just uses it, while the agent drives it over CDP. On a headless Linux host, run it headed under Xvfb + noVNC (https://www.freestyle.sh/docs/guides/run-chromium-and-chrome-in-a-sandbox — read 2026-11-17).
- **Security / isolation:** the debug port has **no authentication of its own** — "anything that can reach it has full control" — bind to `127.0.0.1` only, never expose port 9222 publicly (https://www.browserless.io/blog/chrome-remote-debugging — read 2026-11-17). Sharing the host browser *binary* is fine; sharing the *profile* is what changed — Chrome 136 forces a separate profile with a separate encryption key precisely because "infostealers had taken to using the port to extract cookies" (https://www.mosaicbrowser.com/guides/connect-to-an-existing-chrome-with-cdp — read 2026-11-17). Chrome for Testing is Google's recommended binary for automation scenarios (it "will continue to respect the existing behavior") (https://developer.chrome.com/blog/remote-debugging-port — read 2026-11-17).
- **Anti-bot friction:** a real branded Chrome launched normally and driven over CDP looks the most like a normal browser of all options here — the proxy.wiki measurement found attached-to-a-self-started-Chrome differed on 0 of 15 checks (https://proxy.wiki/research/bot-detection-signals-measured/ — read 2026-11-17). Still not a guarantee; detection also weighs TLS, IP, behaviour.
- **Resource use:** one full Chrome process; no extra driver beyond the CDP client. NOT FOUND as a quantified figure.
- **Licence:** CDP itself is part of Chromium/Chrome; no separate licence applies to using the protocol. (No licence claim found on the pages read — do not cite one.)
- **Verdict:** this is the simplest correct shape if the agent runs on the human's desktop session — but it is *not* isolated from the human's browser beyond the profile boundary (same binary, same machine, same user), and it dies with the desktop session. The container version of the same idea (option (a) + CDP) keeps the profile separation and adds a real isolation boundary, which is why the recommendation below uses the container, not the desktop.

Microsoft's own guidance in that README: coding agents may do better with the **Playwright CLI + Skills** (more token-efficient) and MCP suits "long-running autonomous workflows where maintaining continuous browser context outweighs token cost" — same source.

## 6. Recommendation — the one setup for this exact situation

**Situation:** rootless Podman on Fedora; a 16-thread desktop with 62 GB RAM that is also the human's workstation; a human who wants to watch from any device; an agent that signs into ~10 social/maker sites (YouTube, GitHub, Bluesky, Printables, etc.) and sets up 2FA.

### The setup

1. **Browser container — LinuxServer Chromium on Selkies, rootless Podman.**
   - Image: `lscr.io/linuxserver/chromium:latest` (Selkies viewer on port 3001; see §1e) (https://docs.linuxserver.io/images/docker-chromium/ — read 2026-11-17).
   - Run as a systemd user service (`podman generate systemd --new` / quadlet) so it survives reboots and restarts cleanly. Rootless: the container's root maps to the unprivileged host user, so a container escape buys at most that user's privileges (https://documentation.suse.com/smart/container/html/rootless-podman/index.html — read 2026-11-17).
   - `--shm-size=1gb` (per the LinuxServer docs) and a persistent volume: `~/.config/agent-browser/config:/config` — the agent's whole profile (cookies, logins, extensions, history) lives here and survives container recreation (https://docs.linuxserver.io/images/docker-chromium/ — read 2026-11-17).
   - **Why Chromium, not Brave, in the container:** Brave follows the same shape, but there is no official Brave-maintained container image, and the LinuxServer Chromium image is the best-maintained of the set; use Brave only if its fingerprint/shields behaviour is specifically needed (see §1d). Keep the human's desktop Brave/Chrome untouched — the agent never touches the human's profile.
   - **Why not Kasm Workspaces:** it is a full platform (PostgreSQL, privileged Docker-in-Docker) and ephemeral by default; overkill for one agent browser (see §1b). **Why not neko:** neko is the closest runner-up — WebRTC by default and the simplest multi-user handover — but its profile persistence is a manual bind-mount per browser, its images pin no browser version, and it has no computer-use API; Selkies is the more actively developed streamer in Nov 2026 (2.2.0 on 1 Nov 2026 vs neko 3.2.0 on 15 Oct 2026) and the LinuxServer image wires persistence, GPU detection and the viewer together out of the box.

2. **Control plane — Playwright 1.65.1 over CDP.**
   - Node 22/24/26 on the host (Playwright 1.65 drops Node 20) (https://playwright.dev/docs/intro — read 2026-11-17). Playwright drives the container's Chromium over CDP (`chromium.connectOverCDP()`), with the CDP port bound to loopback only — the debug port has no authentication, so it must never be exposed (https://www.browserless.io/blog/chrome-remote-debugging — read 2026-11-17).
   - **Why CDP to the container's own browser, not `launchPersistentContext`:** the container already owns the persistent profile and the display; attaching over CDP keeps one browser, one profile, one viewer. And a real branded-Chrome-style headful browser driven over CDP is the closest to a normal browser in fingerprint terms (0 of 15 checks differed in the proxy.wiki measurement) (https://proxy.wiki/research/bot-detection-signals-measured/ — read 2026-11-17).
   - For scripted work, Playwright is the library (3 engines, UI mode, screencast, `connectOverCDP`); Puppeteer 25.18.1 is the Chrome-only alternative (see §2).

3. **Agent interface — chrome-devtools-mcp 1.13.0.**
   - Run `npx -y chrome-devtools-mcp@latest` with `--browserUrl` pointing at the container browser's CDP endpoint (or `--userDataDir` at a dedicated profile if run standalone), plus `--no-usage-statistics` (usage stats are on by default) and `--no-performance-crux` unless CrUX traces are wanted (https://github.com/ChromeDevTools/chrome-devtools-mcp — read 2026-11-17).
   - **Why this over Playwright MCP:** it is headed by default, drives a real Chrome, has the smaller and more debugging-oriented tool surface (32 tools in the 1.12.0 test, `--slim` down to 3), and is maintained by the team that ships Chrome. Playwright MCP is the valid alternative if Firefox/WebKit or accessibility-tree snapshots are wanted — but note its README: it "is not a security boundary" (https://github.com/microsoft/playwright-mcp — read 2026-11-17). Either way, treat the MCP-driven browser as untrusted-input surface and keep it on its own profile.
   - If the work grows into autonomous multi-step web tasks (not just a coding agent driving a browser), add **browser-use 1.0.6** (MIT) on top of the same container browser — local Chromium via CDP, `--profile` for the agent profile — and keep its default cloud browser off (default `Browser()` in 1.0 is cloud) (https://github.com/browser-use/browser-use/releases — read 2026-11-17).

4. **Watching from any device — Selkies viewer behind Tailscale (or authenticated reverse proxy).**
   - The Selkies viewer is an HTTPS page on port 3001; reach it over Tailscale (the host is already the human's workstation) or a reverse proxy with real auth. **Never expose it raw:** by default the LinuxServer images have **no authentication** and the web interface includes a terminal with passwordless `sudo` — anyone who can reach the GUI can gain root inside the container (https://docs.linuxserver.io/images/docker-chromium/ — read 2026-11-17).
   - The human watches the same streamed desktop the agent is driving and takes the keyboard/mouse for any captcha, phone check, or 2FA prompt the agent cannot complete. Selkies 2.2.0's display handover lets another tab/device take the display (https://newreleases.io/project/github/selkies-project/selkies/release/2.2.0 — read 2026-11-17).

5. **Logins and 2FA for ~10 sites.**
   - Sign in once per site through the Selkies viewer (human does the 2FA), and let the cookies persist in `/config`. That is the whole persistence story — no password manager integration is needed for the browser itself.
   - For sites where the agent must do 2FA itself: store TOTP secrets in the agent's own vault (not in the repo, not in the container image) and use the site's TOTP flow — Skyvern's native TOTP support shows the pattern, but Skyvern itself is not recommended here (AGPL, see §3e). For SMS/phone checks, there is no reliable agent-only path: the human takes over in the viewer. Expect some sites (notably Google/YouTube) to challenge a fresh container profile and to re-challenge on IP or fingerprint change; keep each site's recovery options current.
   - **Treat `/config` as credentials:** it holds live session cookies for ~10 accounts. Back it up encrypted (e.g. restic/borg to local disk), never commit it anywhere, and never mount it into any other container.

6. **Security posture, in one paragraph.**
   - Rootless Podman (user-namespace UID mapping) + one single-purpose container is the isolation boundary — but note the two countervailing facts: Chromium runs `--no-sandbox` inside LinuxServer images because "the container itself is the sandbox boundary" (https://docs.linuxserver.io/selkies/developer-guide/building-images/ — read 2026-11-17), and the Selkies web UI has no auth by default and a passwordless-sudo terminal (https://docs.linuxserver.io/images/docker-chromium/ — read 2026-11-17). So: Tailscale/auth in front, CDP on loopback only, the agent profile separate from the human's profile (Chrome 136 enforces this anyway), and the container's network egress restricted to what the agent needs if the sites allow it. 62 GB RAM / 16 threads is far more than this stack needs — one Chromium is a few hundred MB plus the encoder; the headroom is for running several agent browsers side by side later, not for this one.

### What this setup deliberately does NOT use, and why

- **Kasm Workspaces** — full platform, privileged DinD, ephemeral by default; overkill for one browser.
- **Browserbase / Browser Use Cloud / Steel Cloud / Hyperbrowser / Anchor** — good products, but they move the brand-account logins (and the 2FA) onto someone else's infrastructure and onto metered cloud browsers; the brief asks for the agent's *own* browser on the home server. Steel self-hosted is the closest cloud-style alternative and is the named runner-up if a clean REST API + profiles + `sessionViewerUrl` matters more than a visible desktop — but it is still in public beta (v0.5.5-beta, secondary-sourced) and its sessions are headless, so there is no headed window to watch.
- **Skyvern** — AGPL-3.0 copyleft, telemetry on by default, cloud anti-bot withheld from the repo, and a High-severity RCE (CVE-2026-123783, published 6 Nov 2026) in the script sandbox (https://mcp.cve.now/archive/2026-11-06 — read 2026-11-17). Wrong licence and wrong risk profile for a home server holding brand logins.
- **Notte** — SSPL-1.0 core; same service-offering copyleft caution as AGPL.
- **Second profile in the human's desktop browser** — works (Chrome 136 forces the separate profile), but it shares the desktop session, the binary, and the machine with the human's browsing, and dies with the desktop session. The container keeps the same profile separation and adds a real boundary.
- **Archived Puppeteer MCP** — unmaintained since May 2025; use Playwright MCP or chrome-devtools-mcp instead (https://www.mymcptools.com/servers/puppeteer — read 2026-11-17).
